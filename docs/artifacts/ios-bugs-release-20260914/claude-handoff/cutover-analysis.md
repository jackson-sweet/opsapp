## Why existing controls do not meet the requirement

| Existing control | Effect | Reason it does not isolate expenses |
| --- | --- | --- |
| `ACCOUNTING_WRITE_ENABLED=false` | Stops both provider push endpoints | Stops other accounting delivery and does not govern v5 edge |
| Connection `sync_enabled=false` | Pauses the entire connection; v5 also checks this value | Stops existing AR/AP and provider sync, not just expenses |
| Connection `sync_direction=pull_only` | Prevents queue-based financial writes | Affects every outbound entity; v5 ignores direction |
| QBO/Sage cron workload circuit/lease | Stops a whole provider worker | Shared with AR/AP; does not fence edge calls |
| Absent Sage flags | Stops candidate Sage worker | Does not stop QBO or live v5 direct writes |
| Missing expense mappings/configuration | Produces setup/review failures in candidate | Mutable user setup, not deployment authorization; v5 uses older mappings/defaults |
| Manually block existing expense rows | Stops those exact rows | New decisions create fresh pending work; none exist yet |

The queue's existing hold/recovery mechanism suffices. Its existing activation controls do not.

## Minimal gate and exact hold semantics

Implemented internal name: `EXPENSE_ACCOUNTING_WRITE_ENABLED`. It is a server-only runtime decision; unset, empty, false, mixed-case or any unrecognized value denies. Only the exact value `true` enables the additional lane. It is an AND with the existing global/provider/connection/identity/authority checks, never a replacement. No customer toggle or automatic enable-on-settings-save.

For a valid owned expense claim while disabled:

1. Preserve the existing ownership/source/operation validation. A foreign worker or wrong source must never mutate the row.
2. Preserve known provider-acceptance/reconciliation handling before assigning an ordinary paused state. An accepted row must not be turned into apparently fresh recoverable work. Checking already-present evidence requires no provider/credential access.
3. Mark ordinary unaccepted work `blocked` with the user-meaningful diagnostic `Expense accounting sync is paused.` Clear its claim locks using the existing guarded method. Do not call token refresh, provider catalogue reads, `prepare`, provider create, acceptance, finalize, or ordinary retry. The claim's single attempt increment remains; do not decrement/reset it through an unguarded write. Explicit authorized recovery later resets attempts through the existing RPC.
4. Do not clear/rewrite source snapshots, provider identity/environment, frozen postings, external IDs, acceptance timestamps, request IDs, idempotency windows or financial events. Frozen work held after an uncertain attempt remains reconcile-only under the existing recovery fence. The gate cannot convert an immutable posting into new safe-to-retry work.
5. If saving the hold fails or loses worker ownership, propagate the failure; do not acknowledge a successful hold, continue into a provider call, or divert into generic retry handling. A surviving stale claim can be recovered by the existing claim RPC and encounters the same disabled gate again.
6. Re-enabling the flag does not automatically reset blocked rows. Existing pending work may proceed after activation; previously blocked work requires its normal guarded retry or reconciliation. There is no blanket queue replay/backfill, source mutation or guessed provider success.
7. Preserve the existing database notification path. A stored blocked row creates the existing durable review entry; do not add a second notification channel. Repeated worker polling does not re-claim it. A safe original/reversal pair can still be cancelled by the existing unwritten-reversal compaction; that is durable no-write handling, not provider delivery.

The paused lane may consume a slot once when a new expense enters a mixed batch, but cannot repeatedly occupy due queue slots. Existing fair ranking and all non-expense dispatch remain unchanged. A SQL claim filter would save that one claim but is unnecessary for this bounded release.

## GET, retry POST and UI behavior

Worker enforcement is the financial boundary, but leaving the current UI unchanged would offer a retry that immediately re-blocks and increments the notification incident again. That is avoidable and should be included in the bounded gate patch.

- Add the gate read to the expense-specific review service/GET response. For a row that otherwise qualifies for `retry`, return typed recovery `paused` while disabled and render plain paused copy with no Retry action. Do not hide the expense or claim that accounting succeeded.
- Preserve existing safety precedence: accepted/external/request/idempotency evidence, frozen postings, invalid source/event and changed provider identity remain `reconcile`, regardless of the flag. Existing connection problems may retain their connection advice. Paused must never overwrite a stronger reconciliation requirement.
- In expense-issues POST, retain authentication/permission and input validation, then return HTTP 409 with paused copy before `retry_expense_accounting_before_write` when disabled. This stops stale browser pages or repeated direct endpoint requests from churning the queue. Do not call the RPC or modify settings/queue on that response.
- Check the gate again inside the worker, independently of GET/POST. A stale response or a request racing a redeploy cannot itself grant a provider write. Existing service-only RPC ACLs remain unchanged.
- Gate values live per deployed runtime. This is a default-off activation boundary, not an instantaneous revocation of already-running enabled requests. Any future disable must include draining/observing existing invocations before declaring provider quiescence; never clear uncertain acceptance to force recovery.

### Why the bootstrap and edge order matter

Installing the full web candidate before the lifecycle database is unsafe: it removes client sync calls before durable capture exists. Installing the lifecycle while v5 remains active permits old clients to invoke the direct writer concurrently with newly recorded financial work. Relying on production's old generic QBO worker to ignore expenses is also unsuitable: it has no expense case, loads credentials before its unsupported preparation path fails, and can churn attempts/review. A tiny initial queue-hold deployment avoids those mismatched-runtime paths without pausing other accounting.

There is still a short, explicit adapter-to-schema compatibility interval. Approval remains a committed business decision, and current web source treats adapter failure as best-effort rather than rolling approval back. Before migration capture, those approvals have no new ledger event. Record the exact interval and identify affected approved/reimbursed rows read-only afterward; retain them as legacy reconciliation work, never silently backfill/replay provider transactions. The lifecycle intentionally flags pre-migration approval history for review when encountered. If absolutely zero expense-delivery interruption is required, the current rollout needs a separately designed expense-only maintenance/durable-ingress bridge; do not pretend a cross-platform atomic cutover exists or silently broaden this patch. No AR/AP interruption is needed for the recommended sequence.
