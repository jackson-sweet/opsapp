## Blocking findings (required changes to the runbook before execution)

### B1. No per-stage rollback section; the v5 prohibition is not in the runbook

**Claim.** The runbook must state, per stage, the exact rollback action and that after the bundle commits the old direct writer is never restored.

**Evidence.** `cutover-analysis.md` contains no rollback vocabulary at all (`grep -in "rollback|roll back|revert|restore"` matches only lines 57, 65, 92, 97, 104 — none is a rollback instruction). The requirement lives only in `HANDOFF.md:54` ("After capture starts rollback retains hold/adapter and financial custody, not the old direct writer. Final runbook review must verify this precisely.").

Rollback targets verified from source:

- **Stage 1 (hold deployed, schema absent).** Rollback = re-point the production alias to `dpl_138EdNzoYSP4peM1qg9Yk5H7rWdF` (`deployed-runtime-settings-p9.json:3`). Safe: no expense rows can exist, and the hold touches nothing else (`compatibility-hold/production-compatibility-hold.patch:13-15, 48-52` are the only runtime branches).
- **Stage 2 (adapter deployed, schema absent).** Restoring v5 is the pre-release production state and is permissible *only while the bundle has not committed*. The instant the bundle's `COMMIT` (bundle line 2510) lands, restoring v5 would reintroduce a writer that ignores the queue, the gate, and `sync_direction` (`cutover-analysis.md:18`) alongside durable capture — this must be written as a hard prohibition, not implied.
- **Stage 3 (bundle committed).** There is no reverse migration in the bundle or the four constituents. "Rollback" of a committed bundle is *retention*: keep the hold deployment and the adapter serving; do not drop the new relations (that would destroy captured `expense_accounting_events`). A failed bundle rolls itself back (single transaction, `atomic-install/expense-release-atomic.sql:2` `BEGIN;` … `:2510` `COMMIT;`, guard at `:6-52` inside the transaction).
- **Stage 4 (candidate deployed).** Rollback target is **the hold deployment ID**, never `dpl_138…`. With the schema installed, `dpl_138…` (plain production) would route an expense row through `prod:src/app/api/cron/accounting/quickbooks/push-queue/route.ts:1090-1098`: `assertSupportedOperation` passes for `create`, `assertConnectionWritable` passes, `getValidToken` runs (OAuth refresh), `preparePush` (`:769-789`) has no `expense` case and returns `undefined`, `performProviderWrite` (`:810-817`) throws a `TypeError` before any provider call, `classifyError` (`:195-236`) yields `retry`, `scheduleRetry` (`cand:src/lib/api/services/accounting-sync-queue-service.ts:139-180`) backs off and blocks after 5 attempts. No provider write, but five token refreshes per row and an internal `TypeError` string persisted as `last_error` (which the candidate later renders as `reason.unknown`). Custody survives; it is still the wrong target.

**Required change.** Add a "Rollback by stage" section with the four targets above, the hold deployment ID recorded at stage 1 (currently no placeholder exists — `grep dpl_ claude-handoff/*.md` finds only `dpl_138…`), and the sentence: *After the bundle commits, v5 is never redeployed under any rollback.*

### B2. Deploy mechanism unspecified; `main` auto-deploy can silently un-ship the release

**Claim.** The runbook says "Preserve the known production base; do not push the divergent shared main" (`cutover-analysis.md:64`) but never says how the hold or the candidate reaches production, and does not address what happens on the next push to `main`.

**Evidence.**

- `origin/main` is `e26310f4c` — four commits past production `b5b0cb592` (all auth/onboarding, none touching accounting: `git diff --stat b5b0cb592 origin/main -- src/app/api/cron/accounting … supabase/migrations` is empty). Those four never reached production (dashboard shows production still at `b5b0cb592`), so `main` is already in a "will deploy something else on next successful build" state.
- The candidate (`d2d7457f1`) and hold (`e6336445f`) are detached commits off `b5b0cb592`. Neither worktree has a `.vercel/project.json`; only `ops-web/.vercel/project.json` is linked (`prj_hglAp4p8MWheqpQn0UDTygVwlziU`).
- If anyone pushes or merges to `ops-web` `main` after stage 4, Vercel builds `main` (no hold, no gate, no expense processor) and auto-assigns the production domain → production regresses to the B1 stage-4 failure path while the schema keeps capturing.

**Required change.** State the exact mechanism and the guard:
1. From the hold worktree (linked, or `--cwd` with the project link copied in — `project.json` contains no secret): `vercel deploy --prod --skip-domain` → record the deployment URL/ID → verify it (routes respond, `maxDuration`, source commit) → `vercel promote <id>`. Same for the candidate at stage 4. `--skip-domain` matters: it builds with **production** environment variables (so the `EXPENSE_ACCOUNTING_WRITE_ENABLED` absence check in B4 is meaningful) without switching the alias, and lets stage 4 be a promote rather than a build during the 3→4 interval (see B5). Rollback at any stage is `vercel rollback <previous-id>` (instant alias move, no rebuild). CLI semantics are stated from general knowledge, unverifiable from source — confirm on the day and record the actual commands run.
2. A standing rule, in the runbook and told to Jackson in plain words: **no push or merge to `ops-web` `main` until `main` contains at least the candidate's 71 paths** (`git diff --name-only b5b0cb592 d2d7457f1 | wc -l` = 71). The alternative — switching the Vercel project's Production Branch to a release branch that holds the candidate — is cleaner but needs a push and a project-setting change; both are Jackson's calls (see Open questions).

### B3. Legacy-interval reconciliation has no query and no recorded timestamps

**Claim.** `cutover-analysis.md:75` says "Record the exact interval and identify affected approved/reimbursed rows read-only afterward" but names no timestamps and no query, and the mechanism it relies on ("The lifecycle intentionally flags pre-migration approval history for review when encountered") only fires when a row is *next touched*.

**Evidence.**
- Approvals during the interval are committed and their sync call is fire-and-forget on both clients: `prod:src/lib/api/services/expense-approval-service.ts:402-437` (`console.warn` only); field iOS `ops-ios` commit `de994bca~1:OPS/Network/Supabase/Repositories/ExpenseRepository.swift:108-121` (`print` only). The iOS removal (`de994bca`, 2026-09-12) is on no remote branch, so the App Store build still calls the adapter — confirm, but assume yes.
- After the bundle: `private.capture_expense_accounting_state` (`cand:supabase/migrations/20260912203328_expense_accounting_lifecycle.sql:468-479`) creates the state row with `legacy_review_required = p_prior_eligible or accounting_sync_id is not null` and appends a `review` event only when the expense is next mutated (trigger `:516-540`), an allocation changes (`:582-591`), or `request_expense_accounting_sync` is called (`:626`). An interval approval that is never touched again produces nothing — not an error, not a review row, not a notification. It is not "lost forever" (any later touch surfaces it), but it is invisible until then.
- `request_expense_accounting_sync` returns `needs_review` for such rows (`:631`) — so the *web hold build's* post-approval adapter call (which now succeeds against the RPC with the user's bearer, `prod:src/lib/supabase/helpers.ts:98` client → `functions.invoke`) will actually create the review row for approvals made **after** stage 3. The gap is strictly [T2, T3].

**Required change.** Record T2 = adapter confirmed serving (stage 2) and T3 = bundle `COMMIT` (from ledger readback). Immediately after stage 3, run read-only (service role, no mutation):

```sql
select e.id, e.company_id, e.status, e.updated_at, b.reviewed_at
from public.expenses e
left join public.expense_batches b on b.id = e.batch_id
where e.deleted_at is null
  and e.status in ('approved','reimbursed')
  and e.accounting_sync_id is null
  and (e.updated_at between :t2 and :t3 or b.reviewed_at between :t2 and :t3)
  and not exists (select 1 from private.expense_accounting_state s where s.expense_id = e.id)
order by e.updated_at;
```

(`expense_batches.reviewed_at` is what approval sets — authority migration `:146`; `expenses.approved_at` is only written by the direct-write paths, `prod:expense-approval-service.ts:460-465`, iOS `ExpenseRepository.swift:82-94`.) Record the result set with the release evidence. State that these rows are **not** auto-queued and that any later handling is an explicit operator decision under the activation approval — never a replay.

### B5. Stage 3→4 interval is unbounded and customer-visible

**Claim.** Between bundle commit and candidate promotion the hold build is serving with the schema live. Every approval in a company with an eligible push connection (one QuickBooks company today, `expense-report.md:17`) creates a queue row → the hold blocks it → the DB trigger inserts a **persistent** notification.

**Evidence.** `lifecycle.sql:899-926` `notify_expense_accounting_review`: on `blocked`/`needs_review`/`failed` inserts `type='accounting_sync'`, title `Expense sync needs review`, body `Review the expense in accounting settings.`, `persistent=true`, `action_url='/settings?section=accounting&expenseConnection=<id>'`, for every admin with both `accounting.manage_connections` and `expenses.approve`. In the candidate this link opens the manage modal with the PAUSED list (`cand:src/components/settings/accounting-tab.tsx:145-147`).

**Required change.** Bound the interval: build the candidate deployment with `--skip-domain` *before* stage 3 so stage 4 is a promote (seconds, no build risk); require stage 4 within one worker cycle (< 20 min, cron `14-59/20` UTC hours 13-23,0-4 — `cand:vercel.json:228-230`); and add the rollback consequence: rolling stage 4 back to the hold deployment re-creates this dead-end for the duration.
